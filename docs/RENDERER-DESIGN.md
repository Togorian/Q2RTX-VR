# Renderer services and temporal history

Quad Views was a central design goal for the path-traced VR renderer. Quad Views renders four views: one focus view and one peripheral view for each eye. It can use fixed or eye-tracked foveation. Eye-tracked Quad Views implements dynamic foveated rendering (DFR). Work on denoising, temporal history and focus-to-periphery transitions helps the views form a more consistent image. Standard stereo and fixed-foveation rendering remain supported; hardware, runtime and settings determine available features, performance and image quality. See [requirements](REQUIREMENTS.md).

The release renderer now owns its VR services directly. B1/B0U replay, scripted cameras, captures, witnesses, poison/oracles and diagnostic resource owners are omitted from the selected build. The historical source files remain available for provenance.

The private interface is `source/current/renderer-services557/source/vkpt_vr_services.h`. Implementations remain in their owning renderer units. There is no new runtime controller or optional diagnostic runtime owner.

| Service | Implementation and contract |
|---|---|
| `vkpt_vr_history_parity` | Selected renderer `main.c`: all views use the logical frame index; ordinary rendering uses the renderer frame counter. ASVGF consumers use `VR_HISTORY_PARITY`. |
| `vkpt_vr_history_image` | Selected renderer `main.c` and `textures.c`: validate the image index, activation and selected view; route two-view and four-view temporal images to their existing banks. ASVGF barriers use `VR_HISTORY_IMAGE`. |
| Entity, IQM and weapon history | `vr_seed_entity_history`, `vr_find_weapon_entity` and existing B2 cadence code retain identity mapping, transforms, pose/lerp indices, IQM copies and per-view weapon history. They are independent of a B1 replay owner. |
| `vkpt_vr_require_maintenance_open` | Preserve the seven named world operations and matching registration epoch. Player uploads require completed view masks, closed mirror/surface ownership and no pending pair/first frame. UI texture writes require the existing between-eye boundary and successful device idle. Failure latches terminal ownership and requests stop. |
| Checked allocation and upload | Texture specifications, real Vulkan requirements, compatible memory types, device-local heap budget/usage and actual sums remain checked. Light-statistics clear, light/IQM/UBO transfer barriers, checked buffer allocation/map and BSP completion remain real operations. Diagnostic generation ledgers and coverage resources are omitted. |
| Device/completion failure | `vkpt_vr_latch_device_loss`, `vkpt_vr_abandon_children` and a latch set only after successful queue submission preserve unproved-completion teardown. Failed end does not submit; failed idle does not reset command buffers. Child destruction is skipped when completion is unknown, leaving reclamation to device teardown. |

`REFERENCE_VR_HISTORY=1` replaces B0P in the selected engine and affected shader commands. Its temporal UBO members retain their order, types, offsets and padding. Ray tracing also retains the logical-frame `prev_adapted_luminance` latch; this shared rule previously lived under B1. Normal lighting, display tone curve, bloom, ET/foveation, denoising, geometry and history work remain.

The selected C recipe omits `engine_035` and `engine_036` and all B0P/B0U/B1 compile flags. It contains 130 engine and 50 game translation units, plus the separately defined launcher/resources. Every actual compatibility header supplying the affected ABI includes the private interface. Source-root includes are appended after existing ordered includes; this also fixes the source556 named-header dependency in engine and game consumers.

The shader recipe contains 51 runtime variants and six embedded arrays. The two standalone B1 coverage/descriptor-route modules are omitted. Diagnostic readback tails (283 tone, 162 lighting and 960 HF words) and their observer operations disappear. The six-member normal readback prefix remains 32 bytes. ASVGF capture-only helper includes and tone witness-only barriers are omitted with their observers; ordinary computation and synchronisation remain. The two crosshair arrays are regenerated from the selected GLSL using `tools/embed_spirv.py`; the other four arrays are byte-identical. `recipes/shader-plan.json` and `packaging/payload-plan.json` pin the new selection. Older correspondence records describe their historical inputs.

The stopped controller quit caller is corrected separately: controller mode reaches the existing quit-only reader without first requiring ordinary interaction readiness, whose refusal predicate contradicts quit-only mode. The reader still checks runtime focus, tracking, head/action freshness and identity; deliberate chord/rearm and keyboard desktop-focus rules remain. Normal interaction readiness is unchanged.

Historical checks (12 November 2026): these fixtures are not retained in this repository. Source557 verification uses actual production functions and headers with explicitly controlled CPU Vulkan/XR/state stand-ins. The renderer fixture passes 3,423 checks including 27 refusals; the actual quit caller reproduces the previous failure and passes after correction. Forty affected translation units pass final MSVC syntax checks; game046 also passes its affected check. All 57 retained shader commands pass CPU compilation/validation: 27 outputs are byte-identical and 30 have the diagnostic differences described above. Old/new expanded GLSL and SPIR-V interfaces were compared; 188 C static assertions additionally check 181 UBO offsets, six readback offsets and its size.

These results establish scoped source/CPU correspondence, not GPU visual equivalence, headset comfort or product acceptance. At source preparation on 12 November 2026, native product build, final private packaging and human runtime testing were still pending. For a delivered candidate, the corresponding-source archive's `BUILD-RECORD.json` and the runtime folder's `RELEASE-MANIFEST.json` identify the actual build and package bytes. These records do not establish human headset acceptance or public-release approval. No blanket assertion disabling, silent-success substitute, gameplay/resume authority expansion or user save/config migration is part of this separation.
